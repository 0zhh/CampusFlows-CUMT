# CampusFlow / 驿链 · 数据库 ER 图（v2，Docker MySQL 8.4）

> 版本：v2.0 · 2026-11-04
> 目标库：`campusflow`（MySQL 8.4，运行在 Docker 容器 `campusflow-mysql`，宿主端口 3307）
> 与 H2 的关系：**H2 保留为“零依赖演示库”**，MySQL 为“生产形态库”，两者共用同一套 JPA 实体，
> 由 `spring.profiles.active` 切换（`dev` → H2，`mysql` → Docker MySQL）。

---

## 一、总览

系统数据分四块：**站点与布局（空间）**、**场景与仿真（时间）**、**工单与审计（流程）**、**包裹与储位（实体）**。
四块之间通过站点主键 `site_id` 与场景主键 `scenario_id` 连接。

```
  ┌──────────────┐        ┌──────────────────┐        ┌─────────────────┐
  │    site      │1     N │      parcel      │1     1 │   pickup_code   │
  │   站点主档    │────────│   包裹（实体）    │────────│  取件码（唯一）  │
  └──┬───────┬───┘        └────────┬─────────┘        └─────────────────┘
     │1      │1                    │N           ┌──────────────┐
     │       │                     │            │   carrier    │ 承运商字典
     │N      │N                    └────────────│  （1 : N）    │
     │       │                                  └──────────────┘
  ┌──┴────────┴───┐   ┌───────────────┐
  │   rack_row    │1 N│    shelf      │1 N    ┌──────────┐
  │  货架排（空间）│───│   单个货架     │───────│   slot   │ 储位 0..1—1 parcel
  └───────────────┘   └───────────────┘       └──────────┘

  ┌──────────────┐        ┌────────────────────┐
  │   scenario   │1     N │ scenario_site_param │ 每场景每站的常量/倍率
  │    场景       │────────└────────────────────┘
  └──┬────────┬──┘
     │1       │1
     │N       │N          ┌──────────────────┐
     │        └───────────│  demand_bucket   │ 逐桶到件/能力/取件
     │                    └──────────────────┘
     │1                   ┌──────────────────┐
     └──────────N─────────│  simulation_run  │ 一次仿真运行（历史）
                         └────────┬─────────┘
                                  │1
                                  │N    ┌──────────────────┐
                                  └─────│    sim_result    │ 逐桶 Q/I/S/P
                                        └──────────────────┘

  ┌──────────────┐        ┌────────────────────┐
  │  work_order  │1     N │  workorder_event   │ 状态流转审计
  └──────────────┘────────└────────────────────┘

  ┌──────────────────┐
  │  param_version   │ 参数版本（“参数不是数字”的落点）
  └──────────────────┘
```

## 二、实体与关系清单

| # | 实体 | 说明 | 关系 |
|---|---|---|---|
| 1 | `site` | 四个站点的静态档案与物理容量 | 1—N `scenario_site_param`、`work_order`、`rack_row`、`parcel` |
| 2 | `carrier` | 承运商字典（文字使用，不用 logo） | 1—N `parcel` |
| 3 | `scenario` | 三个演示场景 | 1—N `demand_bucket`、`simulation_run`、`scenario_site_param` |
| 4 | `scenario_site_param` | 某场景下某站的处理能力/阈值/初值/自助机台数 | N—1 `scenario`、N—1 `site`；主键 (scenario_id, site_id) |
| 5 | `demand_bucket` | 逐 30 分钟桶的到件、处理能力、取件需求 | N—1 `scenario`、`site`；主键 (scenario_id, site_id, bucket) |
| 6 | `simulation_run` | 一次仿真运行（含随机种子、参数版本、创建时间） | 1—N `sim_result` |
| 7 | `sim_result` | 某次运行下逐桶的 Q/I/S/P 与风险标记 | N—1 `simulation_run`；主键 (run_id, site_id, bucket) |
| 8 | `work_order` | 风险工单 | N—1 `site`；1—N `workorder_event` |
| 9 | `workorder_event` | 工单状态流转流水（谁、何时、从什么到什么） | N—1 `work_order` |
| 10 | `rack_row` | 室内一排货架（含所属列 Z-C1…Z-C6 与坐标） | N—1 `site`；1—N `shelf` |
| 11 | `shelf` | 单个货架（排内第几号、层数、每层位数） | N—1 `rack_row`；1—N `slot` |
| 12 | `slot` | 储位（层、位、当前占用） | N—1 `shelf`；0..1—1 `parcel` |
| 13 | `parcel` | 在途/在架包裹（按批次聚合，可抽样到件） | N—1 `site`、`carrier`；1—1 `pickup_code` |
| 14 | `pickup_code` | 取件码（站内唯一，可反查储位） | 1—1 `parcel` |
| 15 | `param_version` | 参数版本快照（哪些参数、什么值、何时生效） | 独立表，按 version 关联页面展示 |

## 三、基数与约束

| 关系 | 基数 | 约束 |
|---|---|---|
| site → rack_row | 1 : N | `rack_row.site_id` 外键，ON DELETE CASCADE |
| rack_row → shelf | 1 : N | `shelf.row_id` 外键，ON DELETE CASCADE |
| shelf → slot | 1 : N | `slot.shelf_id` 外键，ON DELETE CASCADE |
| slot → parcel | 1 : 0..1 | `slot.parcel_id` UNIQUE，NULL 表示空位 |
| parcel → pickup_code | 1 : 1 | `pickup_code.parcel_id` UNIQUE，`(site_id, code)` UNIQUE |
| scenario → demand_bucket | 1 : N | 复合主键 (scenario_id, site_id, bucket) |
| simulation_run → sim_result | 1 : N | `sim_result.run_id` 外键，ON DELETE CASCADE |
| work_order → workorder_event | 1 : N | 按 `at` 升序展示为时间线 |
| carrier → parcel | 1 : N | `parcel.carrier_code` 外键 |

**三条必须由数据库保证的不变式**：

1. 一个储位最多放一件：`slot.parcel_id` 唯一约束
2. 一件包裹最多一个取件码，站内取件码不重复：`pickup_code(site_id, code)` 唯一
3. 逐桶结果必须能对上守恒式：服务层断言 + `sim_result` 上 `CHECK (q >= 0 AND i >= 0)`

## 四、与现有 JSON 数据的映射

| 现有文件 | 落到哪些表 |
|---|---|
| `data/nanhu_sites.json` + `site_geolocation.json` | `site` |
| `data/demo/scenarios.json` | `scenario`、`scenario_site_param`、`demand_bucket`、`sim_result`（首次启动导入一次） |
| `data/geo/station_layouts.json` | `rack_row`、`shelf`、`slot`（按参数生成） |
| `data/params/param_registry.json` | `param_version` |
| 前端生成的工单 | `work_order`（首次导入）、`workorder_event`（此后每次流转写一条） |
| 仿真 `POST /api/simulation/run` | 新增一条 `simulation_run` + N 条 `sim_result` |

> 迁移脚本 `db/migration/V1__schema.sql`、`V2__seed.sql` 由 `data/research/export_mysql_seed.py` 生成，
> 保证 JSON 与库里的数一致（脚本会做一次行数与总量校验）。

## 五、刻意不做的东西

- 不做用户表、角色表、登录会话（课程范围内不要求鉴权，前面已定）
- 不做真实运单号与真实手机号（包裹为演示实体，取件码为生成值）
- 不做多校区（`site` 不设 campus_id）
- 不做分库分表、不做读写分离（数据量 10^4 级，MySQL 单实例足够）
