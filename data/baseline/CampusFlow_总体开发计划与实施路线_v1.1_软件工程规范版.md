# CampusFlow 总体开发计划与实施路线（v1.1 软件工程规范版）

> **正式题目（暂定）：** CampusFlow——面向高校多站点物流的高峰容量仿真与辅助决策系统设计与实现  
> **案例背景：** 中国矿业大学南湖校区；使用公开资料构建背景，使用清楚标记的模拟数据完成系统演示  
> **项目性质：** Java 基础应用与开发课程结课工程；个人主导、前后端完整、可运行可答辩  
> **技术路线：** Java 21 / Spring Boot 3.x / MyBatis-Plus / MySQL 8.x / Vue 3 / ECharts  
> **开发方法：** 轻量级迭代开发 + 五阶段软件工程流程 + 五份核心文档模板 + Git 与测试留痕  
> **版本日期：** 2026-10-27  
> **当前状态：** 规划阶段；文中任务、测试和验收标准均为待执行事项，**不代表已经完成**。

## 版本变更摘要

| 版本 | 变化 | 处理方式 |
|---|---|---|
| v1.0 | 明确产品定位、功能边界、仿真模型、技术栈及十阶段实施路线 | 原版保留作历史基线（其阶段编号 0—9，实为十阶段） |

# 一、项目的软件工程方法（轻量级、标准化、可执行）

## 1.1 为什么采用这套方法

本项目不是大型企业系统，不需要成立正式评审委员会、模拟多人的 Scrum 团队，也不需要强行办理复杂的审批手续。但应遵守课程项目合理的软件工程基本要求：**先明确需求，形成可检查的设计，分模块编码和验证，最后交付能复现的成果。**

采用“**五阶段流程 + 十个实施阶段（编号 0—9）**”两层结构：

- **五阶段**说明软件工程上应完成哪一类工作；
- **十阶段**说明 CampusFlow 具体该怎样动手、先做什么、每一步产出什么；
- 开发中允许迭代，某个模块上线前要走完自己对应的“需求明确 → 设计 → 实现 → 测试”小闭环；
- 只设置简单的自查条件，不额外设置企业级审批制度。

## 1.2 五阶段标准流程及其与十阶段的对应关系

| 软件工程阶段 | 核心问题 | 对应技术阶段 | 主要证据 |
|---|---|---|---|
| **① 需求分析** | 要解决什么，如何判定需求被满足？ | 阶段 0、1 | 项目计划书、SRS、需求编号和验收条件 |
| **② 系统设计** | 如何组织系统与数据，算法如何计算？ | 阶段 1、2、3 的设计活动 | 架构图、ER 图、API 契约、算法说明 |
| **③ 迭代开发** | 分模块怎样实现？ | 阶段 2—7 | Java/Vue 源码、可运行版本、Git 提交 |
| **④ 软件测试** | 实际实现是否满足需求？ | 各阶段随做随测，集中于阶段 8 | 测试用例、实际结果、缺陷与修复记录 |
| **⑤ 交付与答辩** | 别人能否运行并理解成果？ | 阶段 8、9 | README、测试报告、演示脚本、源码包 |

**注意：** 这不是线性地“写完设计后永远不能修改”。例如阶段 6 发现仿真参数需要调整，应同步更新 SRS 中对应需求、设计说明、代码和测试，并通过 Git 提交记录变化。

## 1.3 统一的任务完成标准（DoD）

任一 P0 功能，只有同时满足以下条件才标记为“完成”：

1. 需求有编号、输入输出和可以检验的验收标准；
2. 需要的数据库、接口、规则在设计说明中有对应描述；
3. 源码已实现并能在本地运行；
4. 至少验证一条正常路径和一条有意义的异常/边界路径；
5. 测试记录包含预期结果、实际结果与结论；
6. Git 已提交，关键设计和 README（如受影响）已同步更新。

对单纯 UI 文案、小样式调整，可采用更轻量的验证，不必机械地创建完整需求条目。

## 1.4 五份核心文档的分工

| 文档 | 计划文件名 | 什么时候写 | 最少应写什么 |
|---|---|---|---|
| **① 项目开发计划书** | `docs/01-项目开发计划书.md` | 现在，后续更新 | 背景、范围、技术栈、开发阶段、里程碑、风险、交付物。**本文件即为该文档的主体** |
| **② 软件需求规格说明书（SRS）** | `docs/02-软件需求规格说明书.md` | 阶段 1 完成初版 | 角色、业务场景、功能需求、非功能需求、输入输出、验收条件 |
| **③ 软件设计说明书** | `docs/03-软件设计说明书.md` | 阶段 1—4 补齐 | 总体架构、模块与核心类、数据模型、接口契约、仿真算法、状态规则 |
| **④ 软件测试报告** | `docs/04-软件测试报告.md` | 从阶段 2 记录，阶段 8 汇总 | 测试环境、用例、预期/实际结果、缺陷修复、测试结论、需求追踪 |
| **⑤ 使用与部署说明** | 根目录 `README.md` | 阶段 0 起逐步更新 | 环境、安装、启动、数据初始化、主要功能、演示步骤、常见问题 |

业务流程图、ER 图、API 表、算法说明等均作为**设计说明书的章节或附录**保存。为方便工作可以存放源图，但不需要每个图再对应一份冗长文档。答辩 PPT、源码压缩包及必要的 AI 使用记录属于交付附件，不额外扩大“五份核心文档”的数量。

## 1.5 每次迭代遵循的最小闭环

```text
挑选 1 个有编号的功能需求
       ↓
明确验收条件与异常情况
       ↓
补充设计（表、API、类/方法或业务规则）
       ↓
实现 Java / Vue 代码
       ↓
运行单元/接口/页面测试
       ↓
记录结果、修复缺陷
       ↓
Git 提交并更新文档
       ↓
进入下一个功能
```

无需为个人项目召开正式会议；每完成一个模块进行自查即可。有机会时可请老师或同学对需求、核心算法和演示流程提出意见。

# 二、项目定位、边界与差异化

## 2.1 产品定位

CampusFlow 不开发另一套菜鸟驿站或京东快递的业务系统，也不管理真实取件码、扫描出库和物流轨迹。项目定位于**校园多站点的运营数据分析、容量仿真、方案对比与异常协同**。

核心问题（待实际调研验证，而非已证实的校内痛点）：

- 多个运营点的指标能否通过统一模型展示和比较？
- 在高峰条件下，人员、处理能力与营业时间变化会怎样影响积压？
- 运营风险能否转换为可追踪的处理工单？

定位差异：传统 WMS 以包裹/库存的作业正确性为核心；CampusFlow 以**运营决策模拟和跨站点态势观察**为核心。二者有共同的状态、数据、规则与存储思想，但不照搬业务流程。

## 2.2 落地方式与真实性边界

- 使用中国矿业大学南湖校区作为需求背景和演示案例；
- 学校名称、公开站点信息属于背景材料，不代表已经获取其真实业务数据库；
- 可以创建几个**标注为模拟**的站点，模拟分时段到件、处理、取件和容量；
- 若未来拿到经过授权的脱敏汇总数据，可扩展导入接口，不能绕过快递公司授权获取内部数据；
- 校区与站点信息采用配置或数据表，不在算法中硬编码“南湖校区”，便于在其他高校独立部署；
- 第一版不实现多校在线租户平台。

## 2.3 用户与角色

**P0：运营管理员**，负责站点与容量参数、运营数据、仿真方案、异常工单。第一版可使用单管理员的本地演示模式；如果采用登录，则应真正实施鉴权，不做只有前端按钮的“假登录”。

**P1：只读查看者**，仅查询看板与报告，不修改数据。

## 2.4 功能优先级

### P0——第一版必须完成

1. **站点和运营参数管理：** 站点增改查、停用、容量与处理能力配置、参数校验。
2. **运营数据管理：** 分时段运营数据录入、查询、来源标注；批量 CSV/Excel 导入不作为必需项。
3. **多站点看板：** 到件量、处理量、待处理积压、待取库存、容量使用率、风险与时间趋势。
4. **高峰容量仿真：** 配置场景，按小时计算、展示逐时段结果并保存运行记录。
5. **方案对比：** 基准方案与调整方案共用需求输入，比较积压与容量指标。
6. **异常工单：** 从风险创建或手动录入工单、记录状态变更、处理结果与历史。
7. **交付质量：** 初始化 SQL、固定模拟数据、核心测试、README、五份文档、演示脚本。

### P1——核心功能稳定后选做

CSV/Excel 批量导入、日报导出、只读角色、操作日志、批量仿真、多场景敏感性分析、工单提醒。

### P2——当前不承诺

真实物流接口、包裹跟踪、未授权跨公司调拨、车辆路径优化、AI 预测训练、微服务、Kubernetes、消息队列、多租户、复杂 RAG/Agent。

## 2.5 项目成功标准

- 完整的 Vue—Spring Boot—MySQL 系统能在新环境启动；
- 能通过真实后端接口操作、查询与持久化数据；
- 模拟运营看板、仿真运行、方案对比、工单流转形成完整功能链；
- 仿真结果可复算，关键算法有单元测试；
- 模拟数据与真实公开资料严格区分；
- 每项 P0 核心需求可以追踪到设计、实现和测试；
- 本人可以独立解释关键设计与代码，诚实说明 AI 参与情况。

# 三、需求分析方法与标准化模板

## 3.1 需求从哪里来

按以下顺序收集并检查需求：

1. **课程约束：** Java 为核心、完整全栈、源码可交付、可现场展示和答辩。
2. **场景资料：** 公开的校园物流服务介绍，识别高峰、运营、异常处理等真实业务语境。
3. **用户操作：** 运营管理员要完成哪些具体任务。
4. **实现边界：** 数据可能只有模拟数据，不能依赖未授权接口。
5. **验收方式：** 每条 P0 需求在软件里如何被实际操作和验证。

在尚未实际访谈站点人员之前，SRS 中应写明“基于公开资料的场景假设”，不得写成“经学校实地调研确认”。

## 3.2 功能需求统一模板

SRS 中的**关键功能**按以下模板编写：

```text
需求编号：REQ-SIM-001
需求名称：逐小时积压仿真
优先级：P0
参与角色：运营管理员
前置条件：已选择模拟场景并提供合法参数
功能描述：系统依据到件量、处理能力和期初积压，计算逐时段处理量与积压量
输入：期初积压、每小时到件量、每小时处理能力等
输出：逐时段结果、最大积压量、期末积压量
业务规则：输入不得为负数，实际处理量不超过可处理包裹和最大处理能力
异常处理：缺少数据或存在非法参数时提示具体字段问题，不保存无效运行
验收标准：初始积压 0；三时段到件量 [100,150,50]；处理能力 [80,100,100]；
          期末积压依次为 [20,70,20]，重复运行一致
对应设计：DES-SIM-001
对应代码：SimulationEngine
对应测试：TC-SIM-001、TC-SIM-002
状态：待实现
```

这只是模板示例，不意味着实际测试已经通过。一般 UI 美化或小文案不必逐条写成十几字段的需求。

## 3.3 第一版需求编号总表（初稿，阶段 1 细化）

| 需求编号 | 内容 | 优先级 | 初步验收方式 |
|---|---|---|---|
| `REQ-SITE-001` | 站点信息与容量参数管理 | P0 | 创建、修改、停用后数据库和查询结果一致 |
| `REQ-DATA-001` | 分时段运营数据录入与查询 | P0 | 数据持久化、重复数据和非法值可校验 |
| `REQ-DASH-001` | 多站点运营看板 | P0 | 统计结果与数据库测试集手工汇总一致 |
| `REQ-SIM-001` | 逐小时积压仿真 | P0 | 固定案例的逐时段计算正确 |
| `REQ-SIM-002` | 容量风险识别 | P0 | 达到预设阈值时风险规则正确触发 |
| `REQ-CMP-001` | 同场景方案对比 | P0 | 输入可比且结果变化可解释 |
| `REQ-INC-001` | 异常工单管理 | P0 | 工单可流转、可查询历史、非法状态被拒绝 |
| `REQ-DEL-001` | 部署、演示与数据重置 | P0 | 新环境可启动，固定场景可复现 |

## 3.4 非功能需求——必须可验证，不写空话

可以在阶段 1 将下列目标作为**拟定验收值**，在真实设备测试后再调整，并记录测试环境：

| 类别 | 可验证的拟定要求 |
|---|---|
| 正确性 | 仿真数值与手工测试案例一致；输入非法时不会保存错误数据 |
| 可用性 | 用户在界面中可以完成一次场景选择→运行→查看结果→对比的连续操作 |
| 可恢复性 | 重启后仍可查询已保存方案；可用初始化脚本重置演示环境 |
| 性能 | 演示环境下，10 个站点、每站 7 天小时级数据的仿真计算不超过 3 秒（建议目标，需实测，报告硬件与数据规模） |
| 可维护性 | 仿真引擎不依赖 Spring/HTTP/数据库；主要模块职责清楚 |
| 数据安全 | 不提交密码或密钥；不收集真实运单号、手机号等个人数据 |
| 可移植性 | 站点名称由数据库/配置决定；按 README 可在另一台电脑部署 |

若实测无法达到某项指标，应如实记录、分析与调整，不能在报告中虚构通过结果。

# 四、系统设计方案

## 4.1 总体架构

```text
            浏览器（Vue 3 + ECharts）
                        │ HTTP / JSON
                        ▼
          Spring Boot 单体 Java 后端
     ┌──────────┬──────────────┬────────────┐
     │ Controller│ Service      │ DTO / VO   │
     └──────────┴──────┬───────┴────────────┘
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
      SimulationEngine       Mapper
      纯 Java 计算核心          │
                                 ▼
                           MySQL 数据库
```

核心分层要求：

- `Controller` 接口接收与返回，不写核心公式、不拼复杂 SQL；
- `Service` 处理业务规则、事务和模块协作；
- `SimulationEngine` 使用 Java 纯计算对象，**不依赖 Spring、HTTP、数据库**；
- `Mapper` 负责 SQL/ORM 数据访问；
- `DTO`、`Entity`、`VO` 分离外部输入、持久化结构和前端输出。

## 4.2 模块划分

| 模块 | 主要职责 | 主要难点 | 优先级 |
|---|---|---|---|
| 站点配置模块 | 维护站点、容量、处理能力、营业时间 | 参数有效性与配置版本 | P0 |
| 运营数据模块 | 保存站点分时段数据和来源标签 | 时间粒度、唯一性、统计口径 | P0 |
| 看板模块 | 汇总与展示多站点指标 | 聚合查询与展示一致性 | P0 |
| 仿真模块 | 逐时段库存/积压计算 | 数量守恒、容量约束、边界测试 | P0 |
| 方案比较模块 | 同场景参数变更与指标差异 | 比较公平性、输入快照 | P0 |
| 工单模块 | 风险关联、状态流转与历史 | 状态规则和审计 | P0 |
| 数据导入模块 | CSV/Excel 导入与错误报告 | 格式和重复校验 | P1 |
| 知识问答/Agent | 检索规则、调用仿真工具 | 引用与权限边界 | P2 |

## 4.3 业务流程

### 运营分析

`选择站点和时间 → 查询运营数据 → 汇总指标 → 看板展示 → 查看风险和来源`

### 仿真比较

`选择场景 → 填写合法参数 → Java 仿真 → 保存输入快照和结果 → 查看图表 → 复制修改方案 → 同场景比较`

### 异常工单

`识别风险 → 用户确认创建工单 → 指派处理人 → 处理中 → 已解决 → 已关闭（历史可查）`

工单必须有状态流转规则。例如“已关闭”不得直接回到“待处理”，若需要重新处理，应定义重新打开的独立规则而非任意覆盖状态。

## 4.4 数据库初步实体

| 数据表（暂定） | 内容 | 设计要点 |
|---|---|---|
| `site` | 站点基础信息 | 校区、类型、启停状态 |
| `site_capacity` | 容量与处理能力配置 | 处理区和待取区容量、生效时间 |
| `operation_metric` | 分时段运营记录 | `site_id + time_bucket` 唯一性、来源标识 |
| `scenario` | 仿真场景与方案定义 | 需求曲线、配置说明 |
| `simulation_run` | 一次仿真运行 | 输入快照、算法版本、状态和汇总结果 |
| `simulation_result` | 每时段结果 | 时间、到件、处理、取件、积压、风险 |
| `incident_ticket` | 异常工单 | 类型、严重程度、关联运行、当前状态 |
| `ticket_history` | 工单变更历史 | 前后状态、操作人、时间、备注 |

# 五、核心 Java 仿真模型（本项目的技术重点）

## 5.1 业务含义与边界

第一版采用**按小时推进的离散时间仿真**。优先完成单站点模型，然后对多个站点分别计算并进行统计比较。它不模拟包裹运输路线、真实物流公司自动调度或个人取件行为的精确预测。

在每个时段内区分两类库存：

- `Q_t`：时段开始时待处理的包裹；
- `I_t`：时段开始时已处理并等待取件的包裹；
- `A_t`：本时段新增到件；
- `C_t`：本时段可处理上限；
- `S_t`：本时段实际处理数量；
- `D_t`：本时段希望取走的包裹量；
- `P_t`：本时段实际取走数量；
- `K_q / K_i`：待处理区、待取区的容量上限。

核心计算（容量只用于**预警**的第一版）：

```text
S_t     = min(Q_t + A_t, C_t)
Q_(t+1) = Q_t + A_t - S_t
P_t     = min(D_t, I_t + S_t)       # 约定：本时段处理后的包裹可在同一时段被领取
I_(t+1) = I_t + S_t - P_t

风险条件：Q_(t+1) > K_q，或 I_(t+1) > K_i
```

说明：`D_t` 是“取件需求”，`P_t` 是“实际取件数量”，二者不能混用；若使用外部提供的实际取件量，则先校验它不能超过可领取量。通过上述约定，未取出包裹不会凭空消失。

数量守恒检查：

`Q_(t+1) + I_(t+1) = Q_t + I_t + A_t - P_t`。

容量超限时**只产生风险标记，不自动丢弃包裹或伪造调拨**。以后要实现物理容量限制，必须额外建模“未接纳/外部等待”数量并更新守恒条件。

## 5.2 营业时间与处理能力

- 每个时段从方案中读取处理能力；
- 非营业时段默认 `C_t = 0`，由业务规则控制；
- 站点处理能力可以基于“人员数 × 人均处理能力”得到，但人均能力必须被明确标注为假设参数；
- 新增临时人员、延长营业时间属于**情景模拟**，不会自动调整现实排班；
- 对不可实现的配置值进行限制，如负数、空时段和过大步数。

## 5.3 结果与公平对比

每次运行保存：输入场景标识、起始状态、全部分时段输入、容量/能力配置、算法版本、运行时间和逐时段结果。输出至少包括：

- 每小时到件、实际处理、实际取件、期末待处理、期末待取；
- 最大积压、期末积压、待取库存峰值；
- 容量超限的次数与时段；
- 处理能力不足时段；
- 在模拟期限内积压是否清零。

方案 A 和 B 的**到件需求曲线、初始状态和统计期限相同**才直接做效果对比。界面应展示变化的参数和计算后的指标，不将相关性包装成现实的因果结论。

## 5.4 单元测试样例

初始待处理量为 0，`A = [100,150,50]`，`C = [80,100,100]`：

| 时段 | 期初积压 | 新到件 | 处理能力 | 实际处理 | 期末积压 |
|---|---:|---:|---:|---:|---:|
| 09:00 | 0 | 100 | 80 | 80 | 20 |
| 10:00 | 20 | 150 | 100 | 100 | 70 |
| 11:00 | 70 | 50 | 100 | 100 | 20 |

需要同时测试：零到件、零处理能力、取件需求超过可取库存、连续高峰、容量超限、营业时间变化、非法负数、大数输入、重复运行一致性、数量守恒。用 JUnit 记录**期望结果与实际结果**，不只验证“方法执行时没有报错”。

**任务：**
- 实现工单实体、Controller、Service、Mapper；
- 完成创建、筛选、责任人、状态流转与历史记录；
- 支持从风险生成工单；
- 实现前端工单页。

**软件工程动作：** 在设计说明中绘制状态图，更新工单需求与测试用例；测试非法状态流转、关闭后查询以及历史记录一致性。

**交付物：** 工单前后端、状态图、测试结果。

**通过条件：** 风险→工单→处理→关闭全过程可演示；历史有迹可查，非法流转被拒绝。

## 阶段 8：系统测试与工程收尾（约 8—16 小时）

**任务：**
- 全面执行单元、集成、接口和页面验收测试；
- 使用固定正常、高峰、容量风险场景做端到端验证；
- 检查数据初始化、重置、空数据和失败恢复；
- 修复阻塞问题；
- 在新环境按 README 重新部署；
- 检查源码、数据库、文档与演示数据一致性。

**软件工程动作：** **正式形成 `04-软件测试报告.md`**，填写真实通过/失败数据、缺陷清单与修复记录；逐行核对 RTM；在 Git 标记候选发布版本。

**交付物：** 测试报告、缺陷修复、完整 README、候选发布版本。

**通过条件：** 核心测试通过，无阻塞主流程的已知缺陷；按 README 可以重新启动；需求与测试证据可以对应。

## 阶段 9：交付与答辩准备（约 6—10 小时）

**任务：**
- 完整提交源码、SQL、种子数据和五份核心文档；
- 设计 5—8 分钟演示流程；
- 准备架构图、ER 图、仿真算法与手算测试案例；
- 准备实际 AI 参与说明（按课程要求，后续专项整理）；
- 演练现场启动、参数修改、运行仿真、方案对比和工单闭环。

**软件工程动作：** 归档最终版本号、测试结论、已知限制和部署说明；做一次交付清单自查。答辩展示需求→设计→代码→测试的一条完整证据链。

**交付物：** 最终源码包、五份文档、固定演示数据、答辩 PPT/脚本、版本标签。

**通过条件：** 可从干净环境完成演示；能够独立解释核心逻辑；不将模拟结果宣传为真实运营成果。

## 7.1 工作量与里程碑

| 里程碑 | 对应阶段 | 粗略工时 | 主要结果 |
|---|---|---:|---|
| M0 范围确定 | 0 | 3—5 | 计划、环境、仓库 |
| M1 需求与设计草案 | 1 | 6—10 | SRS、流程图、ER 草图 |

**每周工作节奏：** 选择 3—5 项可验证任务 → 完成代码与测试 → Git 提交 → 更新文档和任务状态。无需形式化的每日站会。

# 八、五份核心文档如何编写：可直接照用的目录模板

# 九、Git、版本管理与需求变更

## 9.1 版本管理的最小做法

- 新建仓库后提交项目计划和 README；
- 每完成一组有关联的功能或修复，就提交一次；
- 提交信息说明做了什么，推荐 `feat: ...`、`fix: ...`、`test: ...`、`docs: ...`；
- 不上传数据库密码、API Key、真实个人数据、`node_modules`、`target` 等生成物；
- 每个主要里程碑保留一个能启动的版本，必要时打 Git 标签；
- 不要求个人项目严格使用复杂 GitFlow，可先使用 `main` 主分支配合短期功能分支，或直接按清晰提交推进。

示例提交：

```bash
git add .
git commit -m "feat: implement hourly parcel backlog simulation"
git commit -m "test: add simulation conservation test cases"
git commit -m "docs: update simulation model and API contract"
```

上述仅为命令示例，实际应在有真实文件变更且测试通过后执行。

## 9.2 轻量级需求变更记录

对于影响范围、核心业务规则、表结构或 API 的改动，在计划书的修订记录或 SRS 中加一行即可：

| 编号 | 改动 | 原因 | 影响 | 决策 | 验证 |
|---|---|---|---|---|---|
| CHG-001（示例） | 仿真增加非营业时段规则 | 更贴近站点操作 | 算法、配置、测试 | 待讨论 | 待执行 |

变更后检查是否需要更新：需求编号/验收标准、设计、代码、测试和 README。轻微 UI 调整直接正常提交，不必创建变更单。

## 9.3 个人贡献和 AI 使用的记录原则

本次计划**不展开提示词设计**。但从开发开始，应保留真实的阶段提交、测试与设计决策。日后根据课程要求说明：本人承担了哪些业务设计、Java 核心逻辑、调试测试；AI 对哪些实现提供了建议或初稿；本人如何修改和验证。不能根据“想要怎样答辩”倒推编造贡献记录。

# 十、模拟数据、风险与质量边界

## 10.1 模拟数据准备

准备至少以下五类固定测试场景：

| 场景 | 设计目标 | 答辩可展示内容 |
|---|---|---|
| A 正常运营 | 到件量大致低于处理能力 | 积压稳定、容量不超限 |
| B 持续高峰 | 连续多个时段到件量高于处理能力 | 积压增长、处理瓶颈 |
| C 容量风险 | 处理区或待取区接近/超过容量 | 风险规则触发与解释 |
| D 改善方案 | 在同一需求曲线下提高处理能力或调整时段 | 基准方案和调整方案比较 |
| E 工单闭环 | 由场景 C 产生风险并追踪处理 | 风险→工单→处理→关闭 |

原则：使用公开报道时记录来源和发表日期；公开数据不能凭空推导到各站点的实际比例。人员数量、小时到件、单件处理时间和容量均以模型假设标注，不使用真实学生姓名、手机号码和运单号。

## 10.2 风险表

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 既有系统已有类似运营分析功能 | 差异化不足 | 将成果界定为独立可解释的仿真与方案比较原型；有条件时再访谈确认 |
| 无法拿到真实数据 | 无法验证现实预测精度 | 固定模拟数据和假设，只检验模型内正确性；不得虚称预测准确 |
| 仿真简单到缺乏说服力 | 难以体现业务深度 | 区分处理积压与待取库存、容量和营业时间，重点做好守恒与测试 |
| 仿真过于复杂 | 影响课程交付 | 先单站点、再多站点，禁止提前引入路径优化和机器学习 |
| 同时学习过多技术 | 学习进度拖延 | 先 Java 核心，再 MySQL/Spring Boot，最后 Vue |
| 数据库/API 反复变动 | 联调困难 | 先设计最小模型；变更时同步 SRS、设计、SQL 和测试 |
| 前后端最后才对接 | 集成失败 | 逐接口联调；每个模块有真实后端数据 |
| 页面好看但无法运行 | 答辩风险 | 以完整业务链和固定场景为优先 |
| AI 生成代码无法解释 | 学习和诚信风险 | 保留真实开发记录；自己理解并验证关键逻辑，如实披露 |
| 部署失败或数据丢失 | 无法展示 | README 验证、初始化/重置脚本、备用录屏 |
| 持续加需求 | 项目范围失控 | P0 冻结，P1/P2 不阻塞当前里程碑 |

## 10.3 质量与合规边界

- 第一版是课程系统原型，不冒充经授权上线的矿大官方系统；
- 不处理学校或快递公司的私有运营数据；
- 核心算法输出的是“在给定假设下的仿真结果”，不是对真实物流结果的保证；
- 不因加入 AI 功能而放弃业务规则和数据一致性验证；
- 若老师提供固定的课程规范或模板，以课程要求优先，并按本方法压缩或补充交付物。

## 11.2 建议 5—8 分钟演示顺序

3. **运营看板（约 40 秒）**：查看各站点指标和模拟数据来源。

5. **异常工单（约 40 秒）**：演示从风险到处理记录的闭环。
6. **Java 实现与测试（约 1—2 分钟）**：展示 `SimulationEngine`、关键公式、JUnit 结果与需求追踪。

## 最终执行原则

1. **规模匹配：** 本科课程项目采用轻量标准化，不模仿大型企业审批制度。
2. **真实闭环：** 每个关键需求都有对应设计、代码、测试和验收记录。
3. **Java 为主：** 业务计算和验证由 Java 后端承担，不把核心算法藏在前端或 AI 输出里。
4. **小步推进：** 按模块迭代，每一步都可运行、可回退、可复查。
5. **真实性：** 模拟数据不伪装真实校内运营；测试未执行就不写通过。
6. **文档精简：** 五份核心文档足够，内容可审核比篇数更重要。
7. **答辩可解释：** 本人能够说明设计取舍、核心实现、测试和 AI 的实际辅助范围。

**目标：以标准化、模板化、可追踪的软件工程方法，完成一套边界清楚、可实际执行、可运行、可验证并适合课堂答辩的 CampusFlow Java 全栈工程。**
